# ADR-0033: Embedded MCP server for agent automation

## Status

![Active](https://img.shields.io/badge/Active-green?style=for-the-badge)

## Summary

Pod embeds an off-by-default [Model Context Protocol](https://modelcontextprotocol.io) server in the GUI process so an
external AI agent can drive the app over localhost. It is a hand-rolled JSON-RPC-over-HTTP listener bound to `127.0.0.1`
only, authenticated by a per-install bearer token, with an Origin/Host allowlist to blunt browser-driven attacks. A
typed tool catalog and a five-flag permission gate govern what an agent may do. Tool calls cross into the iced update
loop through a static-sender bridge (the same pattern as the deep-link transport), so tools run on the thread that owns
the live database and reply over a one-shot. The transport, auth, config, lifecycle, bridge, reload signal, and the
registry/gate scaffolding ship here; the read, local-write, and mail tool families plug into the registry in later work.

## Context

Pod holds a capsuleer's full EVE picture (wallet, skills, industry, assets, mail). Exposing that to an AI agent demands
a stable, typed automation surface — MCP is the de-facto standard, so a connected agent can list and call tools the
same way it talks to any MCP server. The hard parts are not the protocol but the trust boundary: the server runs inside
a desktop GUI with a live SQLite database and an iced event loop, so it must (a) never be reachable off the machine, (b)
require an explicit opt-in and a secret, (c) resist the standard localhost attacks (a malicious web page reaching a
loopback service via DNS-rebinding/CSRF), and (d) apply mutations through the one event loop that owns the app state
rather than racing it from a background thread.

The existing deep-link transport (ADR-0005) already solves the "background thread hands an event to the iced update
loop" problem with a static sender stashed by a [`Subscription`](../../src/features/auth/deep_link.rs); the database
already enforces one-writer/many-readers ([ADR-0031](0031-one-writer-many-readers-sqlite-access.md)) so a server reading
a clone of the interactive `Database` serializes safely. This ADR reuses both rather than inventing new machinery.

## Decision

### Transport: hand-rolled JSON-RPC-over-HTTP, not rmcp

The locked direction was streamable-HTTP via [`rmcp`](https://crates.io/crates/rmcp), falling back to a minimal
hand-rolled server if rmcp proved too heavy. A spike chose the **hand-rolled** path:

- rmcp's `transport-streamable-http-server` feature pulls in `schemars`, `tower`, `uuid`, `http`/`http-body`/`bytes`,
  `sse-stream`, and (to actually listen) an HTTP-server stack such as `axum`/`hyper`. That is a large dependency and
  codegen surface for a one-route, one-verb, JSON-in/JSON-out endpoint.
- rmcp's server is built around its own service trait and async-rw transports; marrying that to our
  static-sender-into-the-update-loop bridge (where a tool must run on the iced thread and reply over a one-shot) would
  mean adapting around its model, not using it as intended.
- The protocol slice Pod needs — `initialize`, `ping`, `tools/list`, `tools/call`, plus bearer auth and an Origin/Host
  check — is small and fully serviceable with `tokio::net` (already enabled via `tokio`'s `full` feature) and
  `serde_json` (already a dependency). The result adds **zero** new crates.

The server is therefore a minimal HTTP/1.1 listener: it accepts on `127.0.0.1`, parses the request head and body, runs
the auth checks, dispatches the JSON-RPC method, and writes a `Connection: close` response. Catalog methods
(`initialize`, `ping`, `tools/list`) resolve in-band; `tools/call` is routed to the update loop.

The cost is that Pod owns its HTTP parsing and must track MCP if the spec evolves. That is an acceptable trade for the
dependency and architectural simplicity, and the transport is small enough to swap for rmcp later without touching the
tool registry or the bridge.

### Binding: `127.0.0.1` only

The listener binds the loopback address exclusively, never `0.0.0.0`. The automation surface is for an agent running on
the same machine; it must not be reachable over the network under any configuration.

### Auth: bearer token plus an Origin/Host allowlist

Every request must carry `Authorization: Bearer <token>` exactly matching the configured token; a missing or wrong token
is `401`. The token is `pod_mcp_` followed by 40 hex characters (20 random bytes) generated by `gen_token()` and
persisted in the config; the `pod_mcp_` prefix makes the secret self-identifying. An empty token never authorizes, and a
token is auto-generated on first use when the server is enabled without one.

Because a loopback bearer service is still reachable by a malicious web page in the user's browser, two extra checks
blunt DNS-rebinding/CSRF: any `Host` header present must be loopback (`localhost`/`127.0.0.1`/`[::1]`, with any port),
and any `Origin` header present must resolve to a loopback host. A **missing** Origin is allowed — native MCP clients
send none and the bearer token already gates them — but a browser always sends an Origin, so a cross-site page is
rejected `403`. The route check precedes the token check, so an unknown path is `404` regardless of the token.

### Config: `McpConfig`, off by default, in the TOML app config

A new `McpConfig { enabled: bool, port: u16, token: String, perms: McpPerms }` lives in the TOML app config next to the
accessibility and storage configs (zero DB schema). `enabled` defaults `false` — enabling the surface is an explicit
opt-in. `port` defaults to `7373`. `perms` is the five-flag trust surface `McpPerms { read, local_write, send_mail,
delete_mail, manage_labels }`: `read` and `local_write` default **on**, the three mail/label mutations default **off**,
so the riskiest actions require a deliberate grant. The whole table is omitted from the file while at its default.

### Lifecycle: a controller reconciled against config

A `Server` controller, held by the app, reconciles a live `tokio` listener against the current config: it **starts** the
listener when `enabled` flips true, **stops** it (closing the port and cutting all agent access) when false, and
**restarts** it when the bound port or token changes. The accept loop runs as a `tokio::spawn`'d task ended by a
one-shot shutdown signal, coexisting with iced exactly like the deep-link single-instance listener. The app calls
`Server::apply` on store-open and (in later work) whenever the MCP config changes.

### Bridge into the update loop, and the reload signal

A `tools/call` is not run on the server thread. The accept loop builds an `McpRequest` (tool name, arguments, and a
one-shot reply) and `try_send`s it through a static sender stashed by an iced `Subscription` — mirroring the deep-link
bridge — surfacing as a top-level `Message::Mcp`. The update loop runs the tool against the app's live `Database`,
gated against the **live** config permissions (the authoritative check; the request carries no permission snapshot of
its own), and replies over the one-shot; the accept loop awaits that reply (with a timeout) before responding to the
agent.

Because a write tool mutates the database off the normal sync path, the module defines a coarse data-changed signal:
after a successful mutating tool, the bridge raises `reload::signal()`, delivered as `Message::McpDataChanged`, and the
app reloads the open view through the same drains a sync pulse uses. The write tools themselves land in later specs, but
the signal mechanism is fixed here.

### Tool catalog and permission gate

Tools are registered into a typed `Registry` as `McpTool`s, each carrying the `Permission` it requires and an async
handler. `Registry::dispatch` is the single gate: it refuses an unregistered tool (`unknown tool`) and a tool whose
required permission is off (`permission denied`) **before** the handler runs — handlers never re-check permissions. A1
ships one smoke tool, `ping`, that proves connect → auth → dispatch → reply end to end; the read/local-write/mail
specs add their tools against this registry.

## Affected Areas

- `src/mcp/` — new module: transport, JSON-RPC protocol, auth, lifecycle/server, bridge, reload signal, the tool
  registry + gate, and the `ping` smoke tool.
- `src/config.rs` — `McpConfig` / `McpPerms`, their defaults, the `mcp` field on `Settings`, `gen_token()`, and the
  token auto-generation helper.
- `src/app.rs` — the `Message::Mcp` / `Message::McpDataChanged` variants, the bridge and reload subscriptions, the
  `Server` field and its lifecycle reconciliation, and the update-loop dispatch that runs a gated tool and replies.
- `src/main.rs` — registers `mod mcp`.

## Dependencies

None. The transport is built on `tokio` (already enabled via `full`) and `serde_json` (already a dependency); the rmcp
stack was deliberately not adopted.

## Consequences

### Positive

- The automation surface is off by default, loopback-only, secret-gated, and CSRF/rebinding-resistant — a small,
  auditable trust boundary.
- Zero new dependencies and a small transport that is straightforward to reason about and to swap for rmcp later.
- Mutations apply on the one thread that owns the app state, reusing the proven deep-link bridge and the
  one-writer/many-readers database model; no new concurrency hazard.
- The registry + gate give the downstream read/write/mail specs a clean, single plug-in point with a uniform
  permission check.

### Negative

- Pod owns its HTTP/1.1 parsing and JSON-RPC framing, and must track the MCP spec by hand if it evolves.
- The permission check is authoritative only in the update loop (the accept loop forwards calls unconditionally), so a
  gated-off call still makes one cheap round-trip into the loop before being refused.
- The data-changed reload signal is coarse: a write reloads the active view wholesale rather than patching just what
  changed.

## Future Work

- The Settings MCP tab (enable/port/token/permissions UI) and the actual read, local-write, and mail tool families are
  separate specs that build on this foundation.
- Streamable-HTTP/SSE streaming (beyond the request/response `tools/call`) and an rmcp migration remain open if a future
  client needs them.
