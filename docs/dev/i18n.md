# Internationalization (i18n)

Pod localizes its own UI chrome with [`rust-i18n`](https://crates.io/crates/rust-i18n). Translation strings live in
TOML files under `locales/` at the repo root. The framework is wired in `src/main.rs` (the `i18n!` macro) and the
active locale is set once at startup from the configured language.

## How it is wired

- `src/main.rs` declares `#[macro_use] extern crate rust_i18n;` (exposing the `t!` macro crate-wide) and calls
  `rust_i18n::i18n!("locales", fallback = "en");` at the crate root.
- `src/i18n.rs` exposes `i18n::set_locale(language: Language)`, which maps the `Language` enum to its rust-i18n locale
  string via `Language::esi_code()` (the enum codes — `en`, `de`, `en-us`, `es`, `fr`, `ja`, `ko`, `ru`, `zh` — are
  exactly the locale strings rust-i18n expects).
- `app::boot()` calls `i18n::set_locale(accessibility.language())` once at startup, alongside the existing
  high-contrast and scale application. A language change applies at the next restart (see ADR-0041); nothing swaps the
  locale live mid-session.

## Locale file layout — one file per feature

Each feature module owns its own locale fragment. **Do not funnel strings into a single shared `locales/en.toml`.**
rust-i18n globs `locales/**/*.{toml,yml,yaml}` and merges every file, and for `_version: 1` files (the default) it
reads the locale from **the segment after the last dot in the filename stem**. So:

```text
locales/
  shell.en.toml        # locale "en"      (shell.en  -> last segment "en")
  wallet.en.toml       # locale "en"
  assets.en.toml       # locale "en"
  common.en.toml       # locale "en"      (shared-ui namespace)
  wallet.de.toml       # locale "de"
  _meta.<code>.toml     # one per locale, registers the nine ESI codes
```

Every fragment is merged into one flat key map per locale, so `locales/wallet.en.toml` and `locales/shell.en.toml`
both contribute to the `en` locale without colliding as long as their top-level namespaces differ. This is what lets
each feature's string-extraction task edit a different file: pick **your feature's** fragment and never touch another.

The fragment filename is `<feature>.<locale>.toml`. The English baseline you author is `<feature>.en.toml`. The eight
non-`en` locales are stubbed at the repo level (`_meta.<code>.toml`) so all nine codes register today; the
machine-translated `<feature>.<code>.toml` fragments land later. `en-us` begins as an exact copy of `en` and is
reconciled at the translation capstone.

## Key-namespace convention

Keys are dot-separated and namespaced by their origin:

| Pattern                       | Use for                            | Example                            |
|-------------------------------|------------------------------------|------------------------------------|
| `<feature>.<area>.<key>`      | feature-module UI strings          | `wallet.journal.title`             |
| `config.<enum>.<variant>`     | user-facing labels on domain enums | `config.feature.wallet`            |
| `common.<key>`                | shared, cross-feature strings      | `common.cancel`                    |

In a TOML fragment, group keys under their namespace as a table so the file stays a small, append-only surface:

```toml
[shell.notifications]
mark_all_read = "Mark all read"
title = "Notifications"
```

`<feature>` is the module name (`wallet`, `assets`, `calendar`, `industry`, `mail`, `roster`, `skills`, `settings`,
`shell`, `splash`, ...). `<area>` groups within a feature (`journal`, `transactions`, ...). Keep variants and keys
alphabetical, matching the project's ordering convention.

## Interpolation convention

Use rust-i18n named placeholders — `%{name}` in the locale value, and `name => value` (or `name = value`) when
calling `t!`. Never build user-facing strings with `format!`; interpolate through `t!` so word order can change per
language.

```toml
# locales/shell.en.toml
[shell.notifications]
footer_unread = "%{count} unread"
```

```rust
// returns a Cow<str>; call .into_owned() / .to_string() when an owned String is needed
let label = t!("shell.notifications.footer_unread", count => total);
```

## Missing-key behavior

- A key missing in the active locale resolves to the `en` value (the `fallback = "en"` chain).
- A key absent from every locale resolves to the key string itself and never panics.

Both are covered by unit tests in `src/i18n.rs`.

## Extracting strings (the per-feature task)

1. Add or extend `locales/<feature>.en.toml` with the keys you are introducing, grouped under their namespace table.
2. Replace `text("literal")` with `text(t!("<feature>.<area>.<key>"))` and `format!(...)` user-facing strings with
   `t!("...", name => value)`.
3. Leave the non-`en` fragments to the translation pass — author only the English baseline.

See `src/app.rs` notification chrome (`shell.notifications.*`) for the reference conversion.
